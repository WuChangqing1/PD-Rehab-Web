# 启动与芭蕾会话一致性说明

日期：2026-10-13。依据设计包 `05_患者启动流程与状态一致性.md` 与 `ui_piano_20261013_audit.md`。本子任务修改 `MovementTrainingPage.vue`、`useTrainingStartGate.ts`、`training_start.test.ts`；保留 `TrainingStartController` 和 Gate 的公共接口，未修改钢琴页面、数据库或后端接口。

## 行为

- 无患者时继续浏览动作与方式；点击开始才打开选人，显式 URL 患者优先于共享上下文；已有患者继续核实后 3→2→1。
- 芭蕾准备阶段只解锁音频和保存患者、动作、坐姿/站姿、数据来源快照。准备、倒计时取消、未录制离开都不创建 Session。
- 实际点击“完成并分析”，存在非空录制时才创建 Session；之后创建/分析均使用启动快照，不读取后来变化的患者和配置。
- 分析期间使用互斥锁；创建中的 Promise 共享；已完成录制再次保存会被忽略。上传失败与质量拒绝重录保留 Session ID，重试使用同一记录。创建失败保留录制和配置，可重试。
- 卸载使当前 run 失效，创建或分析的迟到响应不更新界面、不继续迟到上传、不提示成功。
- 活动任务离开有放弃确认，取消确认保留当前录制；分析保存期间阻止路由离开。原先 active 任务不能通过 query 切换患者的保护仍保留。
- 质量拒绝不显示“本次训练已完成”。成功后历史刷新失败会明确提示“指标已保存，但历史记录暂时无法刷新”，避免误报分析失败。
- 浏览时更换患者也重新请求患者资料；已删除患者拒绝绑定，合法选择同步 store 和 query。取消后的旧患者请求无法覆盖新选择。
- “展示分公式未定义，当前为空；这里只展示实际测得的原始指标。”保留在“查看全部原始指标”的折叠区域，符合后台 honesty test，也不占普通结果视图。

## 接口限制

现有芭蕾 API 使用 `startSession` 与 `analyze` 两次请求。准备/倒计时不再写库；但真正开始分析后，若创建已在服务端成功而响应丢失，或上传失败后硬刷新，仍可能留下未完成行。普通上传失败保留同 ID 可重试，路由离开在保存中被阻止；前端无法把两次后端请求改成事务，也不能保证硬终止时清理服务端记录。这些情况不标记为完成或成功。完全消除这一窗口需要后端原子创建分析或幂等/清理策略，本轮未扩展接口。

自动化行为测试没有验证真实摄像头、真实媒体分析或浏览器原生刷新行为；相关浏览器与后端集成验收由主线程报告。

## 浏览器回归补充：倒计时节点（2026-10-13）

真实 Chrome + Vite + 隔离 API 的诊断发现两件不同的事：

1. 准备失败后 `state.phase=idle` 时，Element Plus 的 `modelValue=false`、`visible=false`，外层 `.el-overlay` 已有 `display:none`。旧诊断脚本只读取 `.el-dialog` 直接父层的 `display:flex`，漏查隐藏祖先，误判为弹窗仍可见。保留隐藏 DOM 是该组件默认行为，不是响应式失效；没有为此添加延迟或重建弹窗。
2. 真正的倒计时问题是数字分支 `:key="state.remaining"` 在 3 时，与准备分支自动编译出来的 `key:3` 冲突。Vue 复用同 key 的 div，并保留静态 class：真实 Chrome 得到 `<div class="training-preparing">3</div>`，导致 3 没有倒计时样式，等待 `.training-countdown__number` 中 3 的脚本超时。2/1 的 key 不冲突，样式正常。

修复仅将数字 key 改为 `countdown-${state.remaining}`，维持逐秒重新挂载动画且与准备分支 key 区分。新增直接编译真实 `TrainingStartGate.vue` 模板、使用 Vue renderer 的行为回归，先 RED 于数字 3 的 class，再 GREEN；启动测试现为 **22/22**。另在真实 Chrome 中驱动 Gate 的准备→3→2→1 状态，确认三步均生成正确 `.training-countdown__number` 且准备节点被替换。该浏览器检查使用显式合成阶段，不冒充患者训练，不创建记录；正常音频解锁与真实启动的最终联调由主线程继续进行。
