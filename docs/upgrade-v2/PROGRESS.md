## 第十二轮（"没有无效入口"这条验收标准）新增

### 目标：验收标准里的「页面和按钮没有无效入口」

已有的 `navigation.test.ts` 只检查**静态路由目标**，不检查**运行时按钮是否真的有用**。
所以对 8 个页面做了一次按钮审计。

### 结论（修正工具之后）

> **8 个页面、16 个非破坏性按钮：0 个无反应、0 个报错、0 个 4xx。**

破坏性/启动硬件的按钮（删除、开始录制等）**明确跳过并计数**，没有被静默忽略。

### 但前两次尝试报了 3 个**不存在**的缺陷

| 报告 | 真相 |
| --- | --- |
| 患者档案「详情」→ `Missing required param "id"` | 我用 `element.click()` 点到了**手机端隐藏副本**；正常点击可正确跳转（868 字符，0 错误） |
| 康复训练「进入钢琴训练」→ 404 | 同上；正常点击可正确跳转（1118 字符，0 错误） |

用 JS 的 `click()` **不检查可见性**，而 Playwright 的定位器**会拒绝**点击不可见元素
—— 它拒绝是在帮我，而我绕过了它。

### 这是连续第三轮我的工具报出假缺陷

1. 验证服务器只反代 `/api`（应用调用 `/pd-rehab/api`）→ 误判「生产构建崩了」
2. glob `**/api/**` 拦住了应用自己的源码 `/src/api/*.ts` → 误判「后端一死后端全白屏」
3. JS 点击隐藏元素 → 误判「两个无效入口」

**共同成因：每一次都是我为了"方便"绕过了工具的安全检查。**

已写成 `verification_notes.md`：三个案例、各自的破绽、共同成因、
以及 5 条规则。核心一条：

> **出现"很严重"的结论时，先怀疑自己的工具。**
> 三次的破绽都是一个"对不上的细节"：接口返回 HTML / 公开路由也白屏 / 隐藏按钮报错。

## 第十一轮（离线提示 · 以及我第二次差点报出假缺陷）新增

### 差点报出一个不存在的严重缺陷

我想验证「后端挂掉时界面什么样」。第一次测出来：**7 个页面全部白屏，0 个字符**。
连侧边栏都没有，`#app` 的 innerHTML 长度为 0，`__vue_app__` 不存在 ——
**看起来就是"后端一死，整个应用崩掉"**。这个结论对临床工具来说很严重。

**它是假的。** 我的请求拦截用了 `**/api/**` 这个模式，
而它**同时匹配了应用自己的源码模块** `/src/api/*.ts` —— 我把应用程序代码本身给拦掉了。

把模式锚定到 origin（`http://127.0.0.1:5173/api/**`）之后，真实行为是**正确的**：

| 检查 | 真实结果 |
| --- | --- |
| 页面渲染 | ✅ 完整外壳 + 内容，7 个页面都不白屏 |
| 取不到的数值 | 显示 `—`，**不是 0** ✅ |
| 列表 | 「暂无患者记录」而不是空白 ✅ |
| 说明 | 「无法连接到服务器…」✅ |
| 技术细节泄露 | 无 ✅ |

> **这是连续第二轮我的验证工具"说谎"了。** 上一轮是 API 前缀，这一轮是 glob 模式。
> 两次的破绽都是**一个对不上的细节**：上次是 `content-type` 是 HTML，
> 这次是**连公开路由都渲染不出来**——应用挂载失败不该和登录状态有关。
>
> 教训：**假缺陷比真缺陷更危险**，因为它会让我写出一份自信而错误的报告。
> 遇到"很严重"的结论时，先问一句"我的工具是不是在骗我"。

### U10 · 离线提示是写给运维的，不是写给医生的

真实缺陷比上面那个小得多，但它是真的。后端不可达时界面说：

> 无法连接到后端服务，请确认后端已启动（默认 http://127.0.0.1:8000）。

这是**开发者的话**。医生网络断了，被告知去启动一个回环地址上的进程 ——
他既做不到，也不该看到；而且线上后端其实是 nginx 后面的 `127.0.0.1:18086`，
那个端口号连对的都不是。

**修复**：按构建分流。

| 环境 | 提示 |
| --- | --- |
| 开发（`import.meta.env.DEV`） | 保留开发者提示，端口写对，并提到 `VITE_DEV_BACKEND` |
| 生产 | 「无法连接到服务器。请检查网络连接后重试；若持续无法连接，请联系技术支持。」 |

**验证**：生产产物里 `127.0.0.1:8000` 出现 **0 次**（条件分支被构建期消除），
用户文案存在；开发服务器仍显示开发者提示。

**新增 3 项测试**，其中一项断言开发者提示必须位于 `DEV` 判断**之后**，
而不是一条无条件的 `message` 赋值。

## 第十轮（生产构建产物在子路径下实测）新增

### 此前所有检查都跑在**开发服务器**上

Vite 开发服务器解析模块与路径的方式和静态构建**不一样**。
`VITE_BASE` 配错正是那种「开发时完全看不见、上线后满屏 404」的故障。
所以我用 `VITE_BASE=/pd-rehab/` 构建，再用一个模拟 nginx 行为的服务器真正加载了一遍。

**产物是正确的：**

| 检查 | 结果 |
| --- | --- |
| 资源路径 | `/pd-rehab/assets/index-*.js`，与线上完全一致 |
| 哈希 JS | 200，`text/javascript`，65 KB |
| 深链接 | 200，返回 SPA 外壳而非 404 |
| 子路径之外的请求 | 404（不会误吞其他应用路由） |
| `/pd-rehab/api/auth/me` | 401 `application/json`（确实到达后端） |

**7 个路由**：0 个 404、0 个失败请求、0 个页面级 JS 错误。
与开发服务器共有的 3 个路由**正文长度逐一相同**：634 / 1235 / 1353。

### 但我的验证服务器先说了谎，而且说得很有说服力

它第一版只反代了 `/api`，而 `API_BASE = BASE_URL + '/api'`，
子路径构建调用的是 `/pd-rehab/api`。这些请求落到 SPA 回退上，
**以 200 返回了 HTML**；前端拿 HTML 当 JSON 解析，工作台与患者档案页当场抛 `TypeError`。

**看起来完全就是"生产构建崩了"。我差一点就这么报告。**

真正区分开它的是 **`content-type`**：接口返回 `text/html`，就说明它根本没到后端。

> **教训：验证服务器必须和 nginx 行为一致，否则它会说谎 —— 而且说谎时比真相更有说服力。**
> 一个"看起来像缺陷"的假象，比一个明显的错误更危险，因为它会让我写出一份错误的报告。

## 第六轮（触屏规则首次真正生效）新增

### U07 · 触控目标规则**降低了**部分控件，而不是抬高它们

上一轮我说「没有可推进的工作了」。这一轮去质疑一个自己从未验证过的假设，立刻找出三个真实缺陷。

**假设**：我加过一条 44px 触控下限规则，并一直当作已完成。
**事实**：它写在 `@media (hover: none)` 里，而**鼠标浏览器报告 `hover: hover`** ——
也就是说，**这条规则在我跑过的所有检查里从未生效过**，包括那些我声称「已验证触控目标」的检查。

用 CDP 打开触屏模拟，对每个控件**在开关模拟前后各测一次**，一次找出三个问题：

| # | 问题 | 后果 |
| --- | --- | --- |
| 1 | 选择器带三个 `:not()`，特异性 (0,3,0) **压过** `.pd-big-action` 的 (0,1,0) | 主要操作按钮从 **48px 被压到 44px** —— 与规则本意完全相反 |
| 2 | `:not(.el-button--small)` 把小按钮排除在外 | 小按钮停在 Element Plus 的 **24px**，其中四个页面上的「**更换患者**」就是 24px |
| 3 | Element Plus 分页箭头不是 `.el-button` | 患者列表翻页按钮停在 **32px** |

**修复**：豁免只保留 `.pd-big-action`（它自己声明 48px，不能被压下去），其余一律抬到下限；
分页控件单独覆盖；`OrientationHint` 的「知道了」按钮直接取触控下限。

**触屏模拟下实测（8 个页面）**：

| 页面 | 修复前 <44px | 修复后 |
| --- | --- | --- |
| 评估中心 | **9** | **0** |
| 患者档案 / 手指敲击 | 各 2 | **0** |
| 康复训练 / 钢琴 / 芭蕾 / 随访 | 各 1 | **0** |
| 工作台 | 0 | 0 |
| **合计** | **17** | **0** |

`.pd-big-action` 在触屏与鼠标下**均为 48px** —— 没有任何控件被压小。

**新增 4 项契约测试**，其中一项断言该区块内**不得出现无限定的 `.el-button` 规则**
—— 那种规则会与 `.pd-big-action` 特异性打平、靠源码顺序取胜，从而让「压小」重新出现。

> 教训：**「规则写了」不等于「规则生效了」。** 媒体查询可以整块处于休眠状态，
> 而它恰恰是移动端最关键的那一块。

## 第五轮（真实浏览器对照 · 迁移链验证）新增

### 用真实 Chrome 证实 MP4 可播 —— 并作废一批**看起来正常实则错误**的截图

上一轮发现 Playwright 自带 Chromium 不能解码 H.264。本机装有真实 Chrome，用它做了对照：

| 检查 | Playwright Chromium | **真实 Chrome** |
| --- | --- | --- |
| `canPlayType(avc1...)` | `""` | **`"probably"`** |
| 实际播放 | ❌ `DEMUXER_ERROR` | ✅ **`PLAYED`**，`currentTime=1.2s`，`readyState=4` |

**结论：SOP 产出的 H.264 MP4 在真实浏览器中正常播放**，此前失败纯属工具限制。

**但我随后尝试用真实 Chrome 做多尺寸渲染检查，实测发现这条路是错的，已作废 40 张截图：**

| `--window-size` 请求 | Chrome 实际 `innerWidth` |
| --- | --- |
| 375 / 390 / 430 | **512**（Windows 最小窗口宽度） |
| 768 | **746**（低于 768 断点 → 实际渲染的是手机单列布局） |
| 1024 | 1002 |

手机尺寸的截图实际是 **512px 布局被裁窄**；「768 平板」那张实际是手机布局。
**它们每一张看起来都正常，每一张都是错的**，因此全部删除。

> **分工结论**：响应式尺寸验证交给 **Playwright**（实测请求 390 就是 390）；
> **真实 Chrome 只用于 Playwright 做不到的事**（如 H.264 编解码支持）。

### 一个必须记下的验证环境限制

SOP 标准参数产出的 MP4 在本机 Playwright Chromium 报 `DEMUXER_ERROR_NO_SUPPORTED_STREAMS`。

## 第二轮（验收标准补验）新增

上一轮的报告只 verify 了部分验收标准。本轮逐条补验，**发现三个真实缺陷并修复**。

### 缺陷 1 · 配方事件字段根本没有入库

`PianoEventIn` 接受 `recipe_id` / `pair_role` / `inter_hand_onset_diff_ms` /
`beat_in_bar` / `is_accent`，前端也确实发送，但 service **一个都没写**。

本项目早有约定：这类无列的附加字段存在 `events_extra_json` 侧信道里
（`is_wrong_key` 等一直如此）。我把字段加进了 schema，却没有加进侧信道，
于是它们被接受、被校验、被丢弃，**没有任何报错**。后果是双手配方在计算
同步指标时，读到的事件已经丢失了配对信息，`inter_hand_sync_mean_ms` 报 None。

**已修**，并新增一类测试而不是只修一个实例：断言 `PianoEventIn` 接受的每个字段
要么是真实列、要么在侧信道里。这个测试跑起来立刻又抓到**两个早已在丢的字段**：

### 缺陷 2 · `is_prompt` / `memory_group` 也一直在丢

记忆节奏的 `is_prompt` 标记"这一行是示范、不是提问"。`compute_metrics` 靠它把
示范行排除出所有分母。保存时丢掉这个标记，等于**把系统自己示范的音符算成患者没答上来**，
用根本没发生的失败抬高漏击率。

### 缺陷 3 · 双手配方的第二个键从来没有显示给患者

`secondaryBinding` 只存在于数据层，键盘只高亮第一个键。也就是说：
**界面要求患者按两个键，却只给他看一个。** 这正是任务书警告的
「只增加功能名称或卡片」——功能看起来做好了，实际没法玩。

**已修**：`PianoKeyboard` 新增 `secondaryTargetMidi`，与主目标**同等视觉权重**
（两个键都是必需的，弱化处理会被读成"可选"），会自动滚入视野，
并在图例里明说「两个高亮键都要按」。

### 缺陷 4（我自己引入，被自己的测试抓到）

新增的患者双区布局里写了 `@media (max-width: 1023px)`，不在共享断点
（1199/767/479）之内，被上一轮写的契约测试直接拦下。已改为 767px。
