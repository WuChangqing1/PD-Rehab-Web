## 第六轮（触屏规则首次真正生效）新增

### U07 · 触控目标规则**降低了**部分控件，而不是抬高它们

上一轮我说「没有可推进的工作了」。这一轮去质疑一个自己从未验证过的假设，立刻找出三个真实缺陷。

**假设**：我加过一条 44px 触控下限规则，并一直当作已完成。
**事实**：它写在 `@media (hover: none)` 里，而**鼠标浏览器报告 `hover: hover`** ——
也就是说，**这条规则在我跑过的所有检查里从未生效过**，包括那些我声称「已验证触控目标」的检查。

用 CDP 打开触屏模拟，对每个控件**在开关模拟前后各测一次**，一次找出三个问题：

| # | 问题 | 后果 |
| --- | --- | --- |
| 1 | 选择器带三个 `:not()`，特异性 (0,3,0) **压过** `.pd-big-action` 的 (0,1,0) | 主要操作按钮从 **48px 被压到 44px** —— 与规则本意完全相反 |
| 2 | `:not(.el-button--small)` 把小按钮排除在外 | 小按钮停在 Element Plus 的 **24px**，其中四个页面上的「**更换患者**」就是 24px |
| 3 | Element Plus 分页箭头不是 `.el-button` | 患者列表翻页按钮停在 **32px** |

**修复**：豁免只保留 `.pd-big-action`（它自己声明 48px，不能被压下去），其余一律抬到下限；
分页控件单独覆盖；`OrientationHint` 的「知道了」按钮直接取触控下限。

**触屏模拟下实测（8 个页面）**：

| 页面 | 修复前 <44px | 修复后 |
| --- | --- | --- |
| 评估中心 | **9** | **0** |
| 患者档案 / 手指敲击 | 各 2 | **0** |
| 康复训练 / 钢琴 / 芭蕾 / 随访 | 各 1 | **0** |
| 工作台 | 0 | 0 |
| **合计** | **17** | **0** |

`.pd-big-action` 在触屏与鼠标下**均为 48px** —— 没有任何控件被压小。

**新增 4 项契约测试**，其中一项断言该区块内**不得出现无限定的 `.el-button` 规则**
—— 那种规则会与 `.pd-big-action` 特异性打平、靠源码顺序取胜，从而让「压小」重新出现。

> 教训：**「规则写了」不等于「规则生效了」。** 媒体查询可以整块处于休眠状态，
> 而它恰恰是移动端最关键的那一块。

## 第五轮（真实浏览器对照 · 迁移链验证）新增

### 用真实 Chrome 证实 MP4 可播 —— 并作废一批**看起来正常实则错误**的截图

上一轮发现 Playwright 自带 Chromium 不能解码 H.264。本机装有真实 Chrome，用它做了对照：

| 检查 | Playwright Chromium | **真实 Chrome** |
| --- | --- | --- |
| `canPlayType(avc1...)` | `""` | **`"probably"`** |
| 实际播放 | ❌ `DEMUXER_ERROR` | ✅ **`PLAYED`**，`currentTime=1.2s`，`readyState=4` |

**结论：SOP 产出的 H.264 MP4 在真实浏览器中正常播放**，此前失败纯属工具限制。

**但我随后尝试用真实 Chrome 做多尺寸渲染检查，实测发现这条路是错的，已作废 40 张截图：**

| `--window-size` 请求 | Chrome 实际 `innerWidth` |
| --- | --- |
| 375 / 390 / 430 | **512**（Windows 最小窗口宽度） |
| 768 | **746**（低于 768 断点 → 实际渲染的是手机单列布局） |
| 1024 | 1002 |

手机尺寸的截图实际是 **512px 布局被裁窄**；「768 平板」那张实际是手机布局。
**它们每一张看起来都正常，每一张都是错的**，因此全部删除。

> **分工结论**：响应式尺寸验证交给 **Playwright**（实测请求 390 就是 390）；
> **真实 Chrome 只用于 Playwright 做不到的事**（如 H.264 编解码支持）。

## 第二轮（验收标准补验）新增

上一轮的报告只 verify 了部分验收标准。本轮逐条补验，**发现三个真实缺陷并修复**。

### 缺陷 1 · 配方事件字段根本没有入库

`PianoEventIn` 接受 `recipe_id` / `pair_role` / `inter_hand_onset_diff_ms` /
`beat_in_bar` / `is_accent`，前端也确实发送，但 service **一个都没写**。

本项目早有约定：这类无列的附加字段存在 `events_extra_json` 侧信道里
（`is_wrong_key` 等一直如此）。我把字段加进了 schema，却没有加进侧信道，
于是它们被接受、被校验、被丢弃，**没有任何报错**。后果是双手配方在计算
同步指标时，读到的事件已经丢失了配对信息，`inter_hand_sync_mean_ms` 报 None。

**已修**，并新增一类测试而不是只修一个实例：断言 `PianoEventIn` 接受的每个字段
要么是真实列、要么在侧信道里。这个测试跑起来立刻又抓到**两个早已在丢的字段**：

### 缺陷 2 · `is_prompt` / `memory_group` 也一直在丢

记忆节奏的 `is_prompt` 标记"这一行是示范、不是提问"。`compute_metrics` 靠它把
示范行排除出所有分母。保存时丢掉这个标记，等于**把系统自己示范的音符算成患者没答上来**，
用根本没发生的失败抬高漏击率。

### 缺陷 3 · 双手配方的第二个键从来没有显示给患者

`secondaryBinding` 只存在于数据层，键盘只高亮第一个键。也就是说：
**界面要求患者按两个键，却只给他看一个。** 这正是任务书警告的
「只增加功能名称或卡片」——功能看起来做好了，实际没法玩。

**已修**：`PianoKeyboard` 新增 `secondaryTargetMidi`，与主目标**同等视觉权重**
（两个键都是必需的，弱化处理会被读成"可选"），会自动滚入视野，
并在图例里明说「两个高亮键都要按」。

### 缺陷 4（我自己引入，被自己的测试抓到）

新增的患者双区布局里写了 `@media (max-width: 1023px)`，不在共享断点
（1199/767/479）之内，被上一轮写的契约测试直接拦下。已改为 767px。
