# 二、第一阶段：从 GitHub 获取真实最新代码

## 2.1 核查两个 Git 仓库

已知 Flutter 项目相关仓库为：

`https://github.com/CapriChris/PianoForParkinson`

Web 仓库的真实地址请通过当前本地工作区的 `git remote -v` 确认。

`D:\MyIdea\PianoForParkinson`

以及其下的：

`app`

`web`

`D:\CodingData\Competition\PD\PD-Rehab-Web`

这些只是定位参考，不保证仍为最新工作区。

先通过 Git 和项目文件确认：

- 当前仓库根目录
- 远程仓库 URL
- 当前分支
- 当前 HEAD
- 远程默认分支

- 当前工作区是否存在未提交修改

禁止直接假设 `main` 就是队友刚推送的最新代码。

## 2.2 安全获取远程更新

对于已有本地仓库，先执行：

```powershell
git status --short
git remote -v
git branch -a -vv
git fetch --all --prune
git log --all --oneline --decorate -25
```

注意：

`git fetch` 不会直接修改当前工作区，可以用于安全检查远程代码。

在没有确认本地修改情况前，不得直接执行：

```text
git reset --hard
git clean -fd
git pull --rebase
git push --force
```

若已有未提交代码，应当保留。

优先使用独立 Git Worktree 或独立 Clone 作为本轮 Codex 工作区，避免与队友共用工作树发生冲突。

如果本地缺少 Web 仓库，应先通过已有配置、项目文档或 GitHub 远程信息确认真实仓库地址，再克隆。

不要根据名字猜测 Web 仓库 URL。

## 2.3 确认队友最新 Shorebird 提交

重点检查 Flutter 最近远程提交是否包含：

- `shorebird.yaml` 或实际等效配置

- 基础 Release 或补丁测试记录
- 版本信息
- 对应发布文档
- Android 签名及发布配置

确认这些内容位于哪个远程分支、哪个 Commit。

如果队友的最新成果在独立功能分支上，必须从包含这些成果的正确提交建立本轮基础，而不是从缺少功能的旧 `main` 开始。

如当前存在多个候选分支：

通过实际代码、提交信息和项目文档判断哪个是队友交付的目标版本。

无法确认时，记录候选 Commit 及差异，不得擅自选择明显过时的版本覆盖新成果。

## 2.4 建立本轮独立开发分支

在确认两个仓库的最新、正确基础版本后，分别建立：

不要让两个 Git 仓库相互嵌套。

不要把 Web 仓库的 `.git` 放入 Flutter 仓库。

每个项目保持：

独立仓库。

独立分支。

独立 Commit。

独立 Push。

独立 PR。

如果 Flutter 不需要修改业务代码，可以仅完成只读检查；不得为了让分支有提交而制造无意义的代码修改或空提交。

# 四、任务一：将 AI 文档迁移到服务器并正确渲染

## 4.1 现有问题

目前 AI 问答可能返回 GitHub 文档链接。

用户点击后可能因网络、权限或 GitHub 访问问题无法阅读。

本轮目标：

**用户点击 AI 的来源文档后，直接进入 PD-Rehab-Web 服务器上的文档阅读页面，而不是依赖 GitHub。**

## 4.2 文档发现与分类

扫描两个最新仓库中与产品相关的文档，包括：

- Web 用户使用手册
- Flutter 用户说明
- 账号注册登录说明
- 钢琴训练操作说明
- 舞蹈训练操作说明
- 训练计划说明
- 自动数据同步说明
- 面部视频分析说明
- 报告和随访说明
- 评估指标说明
- AI 问答使用说明
- 常见问题和故障处理
- 其他经过审核、与平台功能相关的文档

建立统一文档清单。

记录：

文档 ID、标题、文件路径、格式、版本、哈希、更新时间、访问权限、适用产品版本。

严禁将 `.env`、密钥、密码、患者隐私、内部安全配置等误作为公开文档部署。

## 4.3 服务器托管

优先使用现有 FastAPI、Nginx 和静态文件能力。

例如设计：

`/pd-rehab/docs/{document_id}`

这是建议形式，实际以当前路由架构为准。

支持 Markdown 正确渲染：

标题、目录、代码块、表格、图片、内部链接、锚点。

支持 PDF 浏览器内预览。

如现有文档使用其他格式，应先检查能否安全转换或预览，不能假装所有格式都可以直接渲染。

必须防止：

- 路径遍历
- Markdown XSS
- 任意服务器文件读取
- 越权访问内部文档
- 失效的相对资源链接

AI 返回的引用统一指向本站可访问的文档页。

文档 ID 应稳定，不因文件移动就全部失效。

## 4.4 增量发布

文档新增或修改时，可以自动更新清单和索引。

不要每次人工修改 AI Prompt 中的静态文档 URL。

对删除或取消授权的文档，应及时撤销展示和检索权限。

# 六、任务三：数据持久化与完整导出

## 6.1 不强制全部数据入数据库

此次需求是：

**业务数据可靠持久化，并且可以被授权导出、备份和恢复。**

不是要求把所有视频、APK、PDF、模型权重和其他大型文件强行写入数据库 BLOB。

可以采用：

结构化业务数据 → 数据库。

大文件 → 私有文件系统或对象存储。

数据库保存：

文件 ID、患者关联、存储引用、SHA256、状态、时间、保留规则。

## 6.2 审计所有业务数据

检查：

患者和工作人员资料。

普通用户账号和关联患者。

训练计划。

计划历史版本。

daily_progress。

钢琴训练。

曲目训练。

舞蹈训练。

训练事件和指标。

App 同步记录。

随访记录。

评估结果。

面部录像元数据。

模型分析结构化结果。

AI 问答记录。

其他现有业务对象。

为每类数据形成：

数据名称 → 生成位置 → 存储位置 → 数据库表或文件 → 主键 → 患者关联 → 保留期限 → 导出方式。

发现数据仅保存在易失内存、未持久化，或无法正常备份时，进行最小必要修复。

不能为了完善导出而重新修改钢琴、舞蹈或模型算法。

## 6.3 业务数据导出

按现有权限模型设计可核验的导出方式。

优先支持：

JSON。

CSV。

已有能力允许时支持 Excel。

导出必须保留：

真实记录 ID。

数据来源。

时间。

任务和指标版本。

指标单位。

原始结构。

必要的关联 ID。

不要在导出过程中偷偷修改原数据。

对于用户无权访问的患者，必须拒绝导出。

不得导出：

密码、密码哈希、Token、恢复码、私钥或服务器密钥。

视频等敏感文件应维持已有授权和保留规则，不能为了“导出完整”而恢复已经删除的视频。

## 6.4 备份与恢复

审计当前数据库和附件备份方式。

说明：

数据库备份策略。

媒体文件备份策略。

恢复顺序。

一致性检查。

备份加密与权限。

现有日志和索引如何重建。

如已经有可靠备份机制，优先验证，不要重新设计。

# 九、修改范围控制

## 9.1 优先 Web 修改

本轮五项主要需求集中在 Web。

Flutter 只在以下情况允许修改：

- 检查与 Web 改动的 API 兼容性
- 必要的版本信息或下载元数据对接
- 直接由本轮需求引起的兼容问题
- 补充必要测试或维护文档

如果 Flutter 不需要代码修改，就不要强行改它。

Shorebird 相关代码原则上只读检查。

自动同步核心算法。

用户注册登录协议。

患者身份映射。

现有数据完整性校验。

## 9.3 Diff 审查

每个修改文件都必须说明：

为什么必须修改。

具体修改了什么。

会影响哪些功能。

通过哪些测试验证。

禁止全项目无关格式化、依赖整体升级和无关重构。

# 十一、Git 协作与提交规则

## 11.1 两个仓库独立提交

完成开发后分别检查：

`git diff --check`

`git diff --stat`

`git status`

`git log`

所有修改必须位于本轮独立分支。

根据实际代码变更进行适当分组提交。

不要将两个项目混合成一个 Commit。

## 11.2 推送分支

Web：

推送到独立的 Codex Web 功能分支。

Flutter：

仅当存在必要的实际代码或文档变更时提交并推送其独立功能分支。

不得通过空提交伪造工作成果。

允许：

`git push -u origin <当前Codex分支>`

前提是确认拥有该分支推送权限，且没有覆盖他人分支。

禁止：

`git push --force`

`git push --force-with-lease`

直接推送到受保护主分支。

自动合并 PR。

自动覆盖队友分支。

## 11.3 分支合并策略

本次开发结束后：

**仅创建或准备 PR，不直接合并。**

在 PR 中明确：

基础 Commit SHA。

修改内容。

测试结果。

风险。

数据库迁移。

回滚方式。

与队友同时修改的文件。

如果队友在此期间继续推送：

可通过 `git fetch` 查看变化。

不要无条件把其新提交直接合入当前分支。

先检查冲突与测试影响，再准备适当的整合方案。

等双方各自完工后，由项目维护人员统一决定合并顺序。
