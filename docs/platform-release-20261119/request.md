# PD-Rehab-Web 与琴伴 Flutter App 综合优化、热更新及正式发布任务

## 一、任务目标

你现在负责 PD-Rehab-Web 和 PianoForParkinson（琴伴）两个项目的完整优化工作。

请直接在当前最新 Git 工作区执行，首先确认真实路径、分支、Git HEAD、未提交变更、当前线上版本和部署拓扑，不要使用旧 ZIP 覆盖最新代码。

本次需要一次性完成以下六项功能：

1. AI 问答引用的文档统一由项目服务器托管，支持网页内正确渲染和阅读。
2. AI 问答基于项目完整、已授权的文档知识库回答与平台相关的问题。
3. 审计全部业务数据的持久化和可导出性，修复缺失的数据保存及导出能力。
4. 在 Web「随访与报告」增加日期筛选和 PDF 报告导出。
5. 在 Web 登录页增加最新 Android APK 下载入口。
6. 为 Flutter App 接入 Shorebird 热更新，验证登录逻辑修改和新增按钮能够通过 Dart 补丁分发。

完成真实开发、测试、预发布验证、Git 交付和符合条件的正式部署。

**最高优先级：不得破坏已有功能、覆盖历史数据、泄露敏感信息，或让新版本导致用户无法登录、训练及同步。**

## 三、任务一：服务器文档托管与在线渲染

### 目标

AI 回答中的文档引用不再依赖用户直接打开 GitHub。

统一使用：

`https://ccqspace.site/pd-rehab/`

下的正式文档查看页面。

### 实现要求

1. 扫描项目中所有适合公开或授权访问的说明文档，包括 README、使用手册、训练说明、评估说明、常见问题和相关技术文档。
2. 建立文档清单，记录标题、来源文件、稳定 ID、版本、最后更新时间、权限级别和内容哈希。
3. 将批准发布的文档部署到服务器文档目录或现有文件存储系统。
4. 提供统一的文档访问路由，例如 `/pd-rehab/docs/{document_id}`，实际路由须与当前前端和 Nginx 兼容。
5. Markdown 需要正确渲染标题、表格、代码块、图片、列表和内部链接。
6. PDF 应支持浏览器内阅读、分页及必要的下载能力。
7. 文档中的相对图片与附件链接应指向服务器上的正确资源。
8. 不允许页面出现 Markdown 源码原样堆叠、图片丢失、中文乱码或跳转 404。
9. AI 引用应使用稳定文档 ID，而不是直接依赖 GitHub URL。
10. 服务器必须校验文档访问权限，不能因为知道文档 ID 就绕过访问控制。
11. 防止路径遍历、任意文件读取、Markdown XSS 和恶意链接注入。
12. 禁止将 `.env`、凭证、患者隐私资料、内部安全配置或未获授权的私有文档发布到公开目录。

不必修改 GitHub 仓库的原始文档结构。

GitHub 可以继续作为源码来源，但用户阅读入口统一由服务器提供。

文档更新时应支持重新发布及清单更新，不能要求每次手工逐条修改 AI 回复中的链接。

## 四、任务二：建设完整的网站文档 AI 问答知识库

### 目标

用户可以在 AI 问答中询问与整个 PD-Rehab-Web 平台相关的问题，并从已授权的项目文档中获得有依据的答案。

例如：

- 系统有哪些训练功能？
- 如何注册、登录和找回密码？
- 钢琴训练的指标代表什么？
- 如何查看和同步训练历史？
- 如何使用面部视频分析？
- 为什么某条记录未同步？
- 如何导出报告？
- 某个模块如何操作？

### 实现要求

#### 1. 完整知识来源

建立统一知识库清单，覆盖实际存在且允许访问的：

- Web 使用文档
- Flutter 使用说明
- 患者与工作人员操作手册
- 钢琴与舞蹈训练功能说明
- 评估及指标定义
- 训练计划与自动同步说明
- 面部视频分析使用说明
- AI 问答本身的使用说明
- 报告与数据导出说明
- 常见问题及故障处理
- 已审核的项目技术说明

先审计实际文档，不能把“扫描过一个文件夹”冒充“已覆盖全部项目文档”。

对于不存在的说明文档，可以依据已验证的现有功能补充准确的用户说明，但不能凭空编造功能。

#### 2. 检索增强问答

优先复用现有大模型接口及 AI 服务。

按当前架构选择适当方案：

- 文档解析
- 分段与元数据
- 全文检索
- 必要时向量检索
- 检索结果重排
- 基于证据生成答案
- 来源引用

不要仅把所有文档直接塞进一次大模型提示词。

要支持增量索引、删除失效内容、版本更新和重复内容去重。

#### 3. 引用可点击

AI 回答引用文档时，应显示用户可读的标题。

用户点击后进入本站渲染页面。

能定位到相关章节或段落时，优先跳转到对应位置。

不能继续默认输出无法访问的 GitHub Raw 链接。

#### 4. 回答可靠性

不能编造不存在的功能、按钮、接口或指标。

文档证据不足时明确说明。

如果文档与当前系统实现冲突，优先标识版本差异，并记录需要人工核实的内容。

#### 5. 权限与敏感数据

区分：

- 普通用户可阅读的使用资料
- 工作人员文档
- 管理员或开发人员内部技术资料
- 患者个人记录及分析结果

知识库检索时也必须进行权限过滤。

普通用户不得通过 AI 问答读取服务器内部配置、其他患者信息或工作人员专用数据。

患者数据仍通过原有受控业务 API 获取，不得将所有患者资料直接混入公共文档知识库。

原有 AI 模型服务、会话记录和隐私授权应保留。

## 五、任务三：全部业务数据持久化与导出能力审计

### 目标

确保平台产生的应保存业务数据有明确、可靠的存储位置，且授权管理人员能够完整、可核对地导出。

**注意：不要求把所有文件二进制内容强制写入数据库。**

大型视频、图片、PDF 和模型文件可以保留在受控文件系统或对象存储中，由数据库保存对应索引、关联 ID、哈希和元数据。

### 审计范围

检查：

- 患者档案
- 普通用户与工作人员账号
- 账号和患者绑定关系
- 训练计划及历史版本
- 训练完成进度
- 钢琴训练原始记录
- 曲目训练记录
- 舞蹈训练记录
- 评估结果
- 训练事件与指标
- 设备与同步记录
- 面部分析任务与结构化结果
- 视频文件及删除状态
- AI 问答会话
- 随访记录
- 报告及报告生成元数据

为每一种数据建立：

数据对象 → 存储位置 → 表或文件 → 主键 → 患者关联 → 保留规则 → 导出方式。

如发现应保存的数据仅存在浏览器内存、临时状态或易失性任务队列中，需要在不破坏原架构的前提下补充可靠持久化。

不得为满足“全部数据入库”要求而重新修改成熟训练算法。

### 导出要求

实现或完善授权数据导出，明确区分：

**业务数据导出：** JSON、CSV，必要时 Excel。

**患者报告导出：** PDF。

**完整备份：** 数据库备份以及必要附件的独立备份清单。

禁止在普通导出中包含：

密码、密码哈希、访问令牌、Refresh Token、恢复码、加密密钥和服务器密钥。

对于视频及敏感文件：

遵守原有用户授权、保存期限和删除要求。

不允许为了导出功能恢复已删除的视频。

导出需有权限检查、必要审计及文件完整性校验。

如果本轮必须增加业务数据导出入口，应优先复用现有管理页面，不新增无必要的顶级导航。

- 正常显示中文
- 分页合理
- 表格不截断
- 图表清晰

下载接口需要验证患者访问权限。

生成的临时 PDF 应有清理机制，不得长期公开保存在静态目录。

## 八、任务六：为 Flutter App 接入 Shorebird 热更新

### 最终目标

以后只修改 Flutter Dart 层：

- 登录页面
- 注册页面
- 按钮
- 页面布局
- 文字
- 状态管理
- 现有 API 调用逻辑
- 不涉及新增原生能力的业务逻辑

时，可以通过 Shorebird Patch 向已安装的用户分发更新，无需重新下载完整 APK。

### 技术要求

首先核实最新版 Shorebird 官方文档、当前 Flutter 版本兼容性、Windows 开发环境、签名方案及实际发布方式。

优先采用官方稳定方案。

不得自己发明“从服务器下载 Dart 源码然后执行”的不安全热更新机制。

#### 1. 首次基础版本

检查现有 APK 是否已采用 Shorebird Release 构建。

如果没有：

需要构建一次支持 Shorebird 的正式基础版本。

对于通过自己网站分发 APK 的方式，使用 Shorebird 官方支持的 APK Release 流程。

确保：

包名不变

签名不变

版本号正确

Flutter SDK 兼容

Android 原生依赖保持正常

用户数据可在覆盖安装后保留。

第一次启用 Shorebird 需要用户安装新版基础 APK。

不得谎称普通旧版 APK 能直接接收 Shorebird Patch。

#### 2. 热更新管理

建立清晰的：

正式基础版本

补丁版本

测试轨道

稳定发布轨道

回滚策略

发布记录。

先在测试轨道验证，不直接向全部用户推送未经测试的补丁。

#### 3. 必须真实验证两个场景

**场景 A：修改登录功能**

例如调整一个登录提示或现有 Dart 层的登录交互。

要求：

不用重新安装 APK。

发布测试补丁。

已安装基础版本的测试设备可以收到补丁。

重新冷启动后变化生效。

账号会话、患者资料和训练记录保持正常。

**场景 B：新增普通按钮**

在合适的低风险测试页面新增一个 Dart UI 按钮，例如打开已有功能页面。

通过另一个测试补丁发布。

验证按钮正常出现并可以使用。

禁止为测试而修改钢琴训练核心逻辑。

测试结束后可将正式 UI 按产品需要保留或恢复，不能留下无用测试按钮。

#### 4. 原生更新边界

若更改：

Kotlin / Java 原生代码

AndroidManifest.xml

原生插件

权限

Flutter 引擎

打包资源

应识别为需要新的完整基础版本。

Shorebird Patch 不能代替原生 APK 升级。

不能为了满足“所有功能热更新”而规避 Android 平台安全机制。

#### 5. App 内更新体验

尽量使用原有 Flutter 页面组件提供：

检查更新

下载中

更新已准备好

重新启动后生效

更新失败

等清楚的状态提示。

普通补丁下载不要打断正在进行的钢琴或舞蹈训练。

不得强制中断训练、关闭正在写入的 SQLite 事务或删除录制中的视频。

若官方运行机制无法提供精确进度，不得伪造百分比。

更新失败应能继续使用已验证的稳定版本。

不要要求患者手工执行命令。

#### 6. 发布分发

网站下载按钮应指向最新版稳定、正式签名的基础 APK。

Shorebird 负责该基础版本对应的 Dart 补丁。

两者的版本与发布渠道必须正确关联。

不能让网站链接到普通 Flutter APK，却声称它能够接受 Shorebird 更新。
