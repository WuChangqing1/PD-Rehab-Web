# 患者编号自动分配（缺陷 #13，独立验收）

普通创建省略 `hospital_number`，后端返回 `P` 加最少六位十进制数字，例如 P000043。编号由 `patient_number_allocations.id` 的数据库原生自增原子分配，再通过患者表既有唯一索引兜底；碰到导入的旧编号会保留该次分配并重试。不是患者数量加一，也不是无锁 MAX 加一。UUID 主键、外键和历史记录不变。

SQLite 使用 INTEGER PRIMARY KEY AUTOINCREMENT，MySQL 使用 BIGINT AUTO_INCREMENT。分配记录永久保留，不随患者软删除/恢复删除。失败且从未对外返回的事务允许数据库回滚；已提交的编号不重用。号码可能有间隙，不保证连续。

迁移 `i5d7e9f1a3b4` 仅新增分配表，读取现有患者编号（包括已软删除），将有符号 64 位范围内 `P` 加数字的最高值作为初始分配水位，不更新任何患者行。其他格式如 DEMO-0001 保持不变。极长的外部编号保留但不作为自增数值水位。

旧客户端创建时仍可传入明确编号；重复编号返回 409。普通页面不提供编号编辑。已有患者编号作为稳定标识，PATCH 不允许改号。完整前缀在所有页面保留，避免 DEMO-0001 与 0001 显示相同。

## 验证范围

- 文件 SQLite、多连接、8 个线程创建 24 个患者，验证唯一、碰撞跳过、删除后不复用。
- 从上一真实 Alembic 版本升级，验证患者 UUID、旧编号及评估外键不变；降级后患者/评估仍保留，再升级通过。
- 自动创建 API、按编号搜索、旧客户端显式编号与重复冲突、只读前端、完整显示标识。
- SQLite 与 MySQL DDL 编译分别验证原生自增关键字。本机未提供 MySQL 实例，因此不声称完成 MySQL 实机并发测试；生产使用 SQLite。MySQL 上线前应在对应实例运行同等多连接创建验收。

## 发布与回滚

升级前停止写入、备份数据库，执行 `alembic upgrade head`，再运行匹配代码。迁移不重建患者表，不更改已有身份字段。

应用代码回滚时优先保留这个加法表；旧代码会忽略它。`alembic downgrade h4c6d8e0f2a3` 仅删除分配表，但会丢失号码预留水位，因此已投入自动编号使用的生产库不应为回滚应用而降级该表。确有需要时，须保留分配表/水位备份；禁止通过清空患者数据恢复。
